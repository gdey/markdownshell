# mdsh v1.5.0 security review

Scope: tag `v1.5.0` (7847fc3, merged from PR #240): everything that changed
since `v1.4.0` (165 commits, 298 files outside `vendor/`), read as a
whole, with the closest look at the fixes for the twelve findings of
[the v1.4.0 review](v1.4.0.md) and at what 1.4.1 and 1.5.0 added: the
`docroot` and `trust` packages, `termsafe`, the env.source and
"outside the repository" questions, the link opener and the `mdsh`
command repair in mdsh-gui, the Events tab and shell-keeping, the cast
player and its replace buttons, the Settings tab, looks, the shell rc
wrapper, front matter that doesn't parse, line edits from the source
pane, and the release workflows. The items the v1.4.0 review listed
under "checked, with notes" and its `--serve` heads-up were looked at
again; their status is at the end.

Threat model, as before and as in `SECURITY.md`: someone opens a `.md`
file they didn't write. Running a block runs its code, which is
expected. A finding is something the file can do **without a block
running** (opening it in `mdsh -i` or mdsh-gui, `-n`, `--html`,
`--pdf`, `-w`), something that **gets around a review gate**
(`confirm`, `--step`, the dependency questions, the env.source and
outside questions, `env.share` and its banner), or something mdsh's own
packaging and release path lets an attacker do to the person who
installs it.

Findings marked *Reproduced* were run against the v1.5.0 code with
throwaway Go tests (not committed), shown in their Repro sections.
Findings marked *Code read* were not run: the container has no display,
so mdsh-gui itself couldn't be launched, and no Linux desktop.

Nothing is fixed in this document's PR. Each finding has a proposed fix
so it can get a thread of its own.

**Status, 2026-11-14:** nothing is left open. Findings 1, 3, 4, 6 and 7
are fixed on `main` (#265, #269, #269, #264, #263); j accepted 2 and 5
as they are. The table's last column has the details.

What 1.5.0 got right is most of the list. Of the v1.4.0 findings, 1, 2,
3, 4 (the Go half), 5, 8, 9, 10, 11 and 12 hold up as fixed on reading
the code, and the fixes are of a piece: one `docroot` helper for every
read and write, one `trust` store for every front end, one `termsafe`
filter for every terminal. The two that don't fully hold are 6 and 7,
below.

## 1. Medium: another copy of mdsh.app still takes over the `mdsh` command

**Where:** `cmd/mdsh-gui/cli.go` `repair`, run in a goroutine at every
launch from `main.go`. The v1.4.0 fix (finding 7) leaves a link that
points into another `mdsh.app` alone *unless* its target "is a place
this app has stood": `slices.Contains(h.known, c.Broken)`. `known` is
`CLIPaths` from the settings (`main.go`: `a.cli.known =
store.Get().CLIPaths`), and `saw` appends this app's bundled path to it
whenever the link is seen pointing at it (`repair`, case `Installed`,
and `install`).

**Why it doesn't hold:** `gui.json` is per user, not per app. Every
copy of mdsh.app the user launches reads and writes the same
`CLIPaths`. The installed app, at `/Applications/mdsh.app`, records
`/Applications/mdsh.app/Contents/MacOS/mdsh` there on every launch. A
second copy, launched from a mounted `.dmg`, a fork's build, or an
older 1.5.x release, reads that list, finds the link's target in it,
and does exactly what the fix meant to stop: removes the link and
points it at itself, with a line in the Console that nobody is looking
at. The honest case the check was written for, "this app moved", is
already covered by the other rule (the target no longer exists); the
`known` rule only ever adds the case where another app stands where
this one stood, which is the attack. `TestCLIOtherApp` asserts this
behaviour as intended, with `known` set by hand.

The impact is the v1.4.0 finding's: the copy becomes the `mdsh` every
terminal runs, and with `sudo mdsh` (design doc, `cli-in-app.md`),
runs as root. It now needs a 1.5.0-or-later copy to be launched once,
rather than any copy, which is why this is Medium rather than
Low/Medium as before: the changelog says it's fixed, so nobody is
watching for it.

**Repro (reproduced):** a test against `cliHost` with one `cliPaths`
slice standing in for the shared `gui.json`:

```go
var cliPaths []string // gui.json's cliPaths, shared by every copy
saw := func(p string) { cliPaths = append([]string{p}, cliPaths...) }
installed := fakeApp(t, filepath.Join(tmp, "Applications"))
os.Symlink(installed, link)
a := &cliHost{bundled: installed, link: link, known: cliPaths, saw: saw}
a.repair() // the installed app launches: cliPaths = [installed]
other := fakeApp(t, filepath.Join(tmp, "Volumes", "mdsh-dmg"))
b := &cliHost{bundled: other, link: link, known: cliPaths, saw: saw}
changed, _ := b.repair()
// changed = "pointed .../bin/mdsh at this app; it pointed at .../Applications/mdsh.app/Contents/MacOS/mdsh"
// os.Readlink(link) == other
```

**Status:** fixed in #265, which drops the `known` rule, `CLIPaths` and
`SawCLI`: a link is repaired only when its target is gone.

**Fix:** drop the `known` rule and repair only a link whose target is
gone (`os.Stat` fails); the moved-app case is that one. If a record of
past places is wanted, key it to the app, not the user: store the
bundle's path *and* something only that bundle has (its code-signing
identifier and team, or a random id written into the bundle at build
time), and compare both. Either way, say in Settings › Shell when the
link was left pointing elsewhere, which 1.5 already does, and make
Install the only thing that moves it.

## 2. Medium: on Linux, "show the file" can open it

**Where:** `cmd/mdsh-gui/links.go` `openLink`: a link to a file that
isn't a markdown file, an image or a type listed in Settings › Files
goes to `a.app.Env.OpenFileManager(target, true)`. That is Wails's
`internal/fileexplorer/fileexplorer_linux.go` `explorerBinArgs`: it
asks `xdg-mime query default inode/directory`, reads that `.desktop`
file's `Exec=` line and substitutes **the file's path** for `%f`, `%F`,
`%u` and `%U` (or appends it), then runs that. `selectFile` is ignored
on Linux. Only when there is no default file manager does it fall back
to `xdg-open <folder>`.

**Impact:** what happens to `thunar /path/to/setup.sh` or `pcmanfm
/path/to/setup.sh` is up to the file manager. Nautilus and Dolphin
open the folder with the file selected; Thunar and PCManFM document a
file argument as "open this file", which for a script means the
desktop's own "run or display?" question at best and running it at
worst, depending on the "execute text files" setting. So a document's
`[setup notes](setup.sh)` can still, on one click, run on some Linux
desktops. The `openable` check (no exec bit) doesn't apply on this
path: it only gates the Settings › Files types. On macOS `open -R` is
a true reveal, and the finding doesn't apply. (Code read: no Linux
desktop here to run the file managers.)

**Status:** j read this on the review's PR and judged it an acceptable
risk; it isn't scheduled. The fix is kept here for the record.

**Fix:** on Linux, reveal the folder, not the file:
`OpenFileManager(filepath.Dir(target), false)`, which makes every file
manager open a folder, and the fallback `xdg-open <folder>`. Or call
the portal / `dbus-send org.freedesktop.FileManager1.ShowItems`, which
is what "reveal" means on Linux, and fall back to the folder. Say
"shown in the file manager" only when it is.

## 3. Low/Medium: a document with no repository gets its whole folder

**Where:** `docroot/docroot.go` `Root`: walking up from the document's
folder, stopping at the home folder or `/`, it returns the first folder
with a `.git`, `.hg`, `.jj` or `.svn` marker, else the document's own
folder. The home-folder rule keeps a dotfiles repository from opening
all of `~` (`TestRoot`), which is right. It doesn't help a document
that *is* in `~`, or in any folder of `~` that holds things the
document didn't come with.

**Impact:** `~/notes.md` has root `~`, so `{<include
file=.ssh/id_ed25519}` reads the key into the rendered view on open, as
v1.4.0 finding 4 described, and `out=image:.zshrc` can overwrite the
rc file when a block runs. The folder untrusted files actually land in
is `~/Downloads`: a document there has every other download as its
root, so an include can read a downloaded `.env` or export, and an
`out=` can overwrite another download. `/tmp` is the same for whatever
is world-readable there. None of this leaves the machine without a
block running, which is why it's Low/Medium rather than Medium; but
"inside its folder" is the whole guarantee the changelog gives, and
for these folders it's a wide one.

**Repro (reproduced):** with `HOME` set to a temp folder holding
`.ssh/id_ed25519` and `Downloads/tax.txt`:

```
Root(~)                                              = ~
Root(~/Downloads)                                    = ~/Downloads
ReadFile(Root(~), ~/.ssh/id_ed25519)                 = "KEY", nil
ReadFile(Root(~/Downloads), ~/Downloads/tax.txt)     = "TAX", nil
WriteFile(Root(~/Downloads), ~/Downloads/tax.txt, …) = nil
```

**Status:** fixed in #269, on j's direction: the root is now the
document's own folder, repository or not, and no hidden file or folder
(a name starting with a dot) under it, which covers finding 4 too.

**Fix:** when there is no repository, make the root the document's
assets folder (`<doc>.assets`) plus the document itself, and treat
anything else in the folder as outside, so it shows up in the outside
question and under `--allow-outside`. If a bare folder must stay the
root for runbooks that live in one, refuse at least the home folder,
the well-known download and temp folders (`~/Downloads`, `~/Desktop`,
`$TMPDIR`, `/tmp`), and any folder not owned by the user, falling back
to the assets-folder rule for those.

## 4. Low: the repository root includes its VCS metadata

**Where:** `docroot.Root` returns the folder holding `.git` (or the
other markers), and `Inside` accepts anything under it, `.git/`
included. Nothing in `includeBlock` (`run/include.go`), `images.inline`
(`report/html.go`), `pdf.renderer.read` or `writeAsset` (`run/run.go`)
sets the metadata folder apart.

**Impact:** `{<include file=.git/config}` is inside the root and reads
on open. `.git/config` carries the remote URL, which people do set as
`https://user:ghp_…@github.com/…` (and `git clone` with a token in the
URL leaves it there); `.git/COMMIT_EDITMSG`, `ORIG_HEAD` and
`logs/HEAD` say what the person has been doing. With `mdsh -w` or a
report that goes somewhere, that's a token out of the repository
without a block running. Writes into `.git/` by a block need the block
to run, so they're the block's own doing and not a finding; still,
`.git/hooks/` is a place where a written file does something later.
The same goes for `.hg/hgrc`, `.jj/` and `.svn/auth`.

**Status:** fixed in #269, whose hidden-files rule (`docroot.Hidden`,
`ErrHidden`) covers `.git`, `.hg`, `.jj` and `.svn`.

**Fix:** in `Inside` (or in `Resolve`), refuse a path whose relative
form starts with a marker folder (`.git/`, `.hg/`, `.jj/`, `.svn/`),
for reads and writes alike, unless `--allow-outside` is set. Mention
`.git` in the outside question's text when a document names it.

## 5. Low: the env.source answer is for names, not contents

**Where:** `trust/trust.go` `Lookup` and `Remember`: the answer is
keyed on the document's absolute path and `slices.Equal` on the list
`run.SourcePaths` gives (absolute, cleaned). `run/session.go`
`prepare` then reads the files when the first shell starts.

**Impact:** two things the question's text ("remembered for this
document, until the list changes") doesn't say:
- The files' contents aren't part of the answer. A runbook in a
  repository that names `./setup.sh` is approved once; every `git
  pull` after that can change `setup.sh`, and the next open runs it
  without a question, as the shell starts, which is before any block
  gate. A file in a shared folder (`~/ops/setup.sh`, the changelog's
  own example) changes the same way. Blocks have the same property,
  but blocks are on screen; a sourced file never is.
- The path is the key. A different document put at the same path (a
  branch switch, a re-clone, a download with the same name) with the
  same `env.source` list is pre-approved.

**Status:** j judged keying the answer on the file names fine as it
is; it isn't scheduled. The fix is kept here for the record.

**Fix:** remember a digest of each file's contents (or size and
mtime) with the list, and ask again when one differs, saying which
file changed; remember a digest of the document's front matter too, so
a replaced document asks again. Show the files' first lines, or a
"Show" button, in the question, so what's approved is what's seen.

## 6. Low: the in-app cast player isn't capped

**Where:** `cmd/mdsh-gui/frontend/src/cast.ts` `parse`: `cols:
h.width > 0 ? h.width : 80, rows: h.height > 0 ? h.height : 24`, then
`new Terminal({ cols: cast.cols, rows: cast.rows, … })` twice (once to
compute frames, once to draw). 1.5 capped `termrec.ReadCast` (1000 by
500, 100,000 events, 16 MB), which covers `--html`, `--pdf`, the
terminal, Copy as GIF and the replace buttons; the player reads the
file itself, through the `/doc/` route (`docfiles.go` serves `.cast`
by type) or from a `cast` fence's body.

**Impact:** a document whose output region links a `.cast` beside it
with `{"version":2,"width":100000,"height":100000}` makes xterm.js
allocate for 10¹⁰ cells as the card is drawn, which hangs or kills the
window. That's the half of v1.4.0 finding 4 that wasn't done. (Code
read.)

**Status:** fixed in #264: the player applies `termrec`'s limits and the
card says the recording is too large.

**Fix:** apply the same limits in `parse` (refuse past 1000 by 500, cap
events and bytes) and show "recording too large" in the card; or have
the player ask Go for the parsed cast, so one parser holds the limits.

## 7. Low: release path, what's left

Read again: `.github/workflows/go.yml`, `gui-packages.yml`,
`release.yml`, `release-notes.yml`, `tap.yml`, `pages.yml`,
`.github/scripts/tap.sh`, `cmd/mdsh-gui/build/darwin/app.sh`,
`build/darwin/dmg/requirements.txt`, `build/linux/appimage.sh`,
`.goreleaser.yaml`.

What's right now: every action is pinned by commit; the tag and
version reach scripts through `env:` and are checked against
`[0-9]+\.[0-9]+\.[0-9]+(-…)?` before anything uses them (`release.yml`
`version` job, `tap.yml`); `dmgbuild` and its dependencies install
with `--require-hashes`; `linuxdeploy` is fetched at a tagged release
and checked by SHA-256; the Neovim tarball in CI is checked; goreleaser
runs `go mod verify`; the release workflow tags only after the
packages built, with `concurrency: release`, and the `notes` job reads
only `CHANGELOG.md` at the tag. v1.4.0 finding 11 is fixed.

Residue, all Low, fixed in #263 (the Hugo `.deb` is checked by SHA-256
and Playwright installs from a lockfile with `npm ci`); the third point
stands as a design note:
- `pages.yml` fetches `hugo_0.147.9_linux-amd64.deb` with a pinned
  version and no checksum, and installs it with `sudo dpkg -i`. The
  site is where the install instructions live, so a swapped package
  could change them. Add the `.deb`'s SHA-256 as the other downloads
  have.
- `go.yml` runs `npm install … playwright@1.63.0` with no lockfile or
  integrity hash, and `playwright install --with-deps chromium`. It's
  CI only, nothing from it ships, so it's a note.
- `.goreleaser.yaml` now has `draft: false` and `release.yml` runs on
  every push to `main` that changes `CHANGELOG.md` with a new dated
  section. That's the design ("release when the release-prep PR
  merges"), and only someone who can merge to `main` can start it;
  it does mean no human looks at the release page before the tap and
  the notes are written. Fine, as long as that's intended.

## 8. Info: checked, with notes

- **`termsafe`** (`termsafe.go`): `Visible` handles C0, DEL, C1 (as
  runes and as a lone 0x9B byte, which it prints as `<0x9B>`), the bidi
  controls and zero-width characters; `Styled` keeps only `ESC [
  digits ; : m` and shows everything else, including `ESC` followed by
  anything that isn't `[`; `SGROnly` drops CSI up to its final byte and
  OSC/DCS/APC/PM/SOS up to BEL or ST. The code at a confirm prompt goes
  through `Visible` everywhere (`cmd/mdsh/main.go`, `tui/view.go`).
  What stays is what SGR itself can do: `ESC[8m` (conceal) hides prose
  or saved output until the next reset, and a foreground that matches
  the background does the same. That can't hide code, only text around
  it; the terminals that honour conceal show it on select. Fine.
  `newPrinter` applies `Styled` only when stdout is a terminal or
  `--color=always`; `mdsh -n evil.md > file` keeps the bytes, which is
  right.
- **`docroot` writes:** `WriteFile` resolves the target through its
  longest existing prefix, re-checks the folder after `MkdirAll`, and
  writes a temp file renamed over the target, so a symlink at the
  target is replaced, not followed, and a symlink in the path can't
  point out. A symlink *inside* the root is followed to its target, as
  documented. `os.Root` would make the check and the write one
  operation; worth it when the minimum Go version allows.
- **`AllowedOutside`** (`run/run.go` `docRootFor`): what mdsh-gui
  allows is the list of paths *as the document writes them*, compared
  as strings, and an allowed path is then read with no root at all. So
  a path approved as `../shared/setup.sh` that later becomes a symlink
  elsewhere is followed. Changing what's at a path outside the
  repository needs a block to run or another program, so this isn't a
  finding; resolving the allowed list at answer time and comparing
  resolved paths would close it.
- **The outside question** (`cmd/mdsh-gui/tab.go`, `service.go`
  `Outside`/`AnswerOutside`, `frontend/src/app.ts`): on open, the
  session is made with the stored answer only (`Outside` looks the list
  up in `outside.json`), so nothing reaches outside before the user has
  answered; the dialog's default button is "Ask me later" and Escape
  is the same; Allow restarts the shells and re-reads the includes. The
  list is recomputed at answer time rather than taken from what was
  shown; a file edited between the two could differ. Small.
- **The trust stores** (`trust.go`): `sources.json` and
  `outside.json` are written 0600 by temp file and rename, in a 0755
  `mdsh/` config folder; they hold document paths. A store that fails
  to parse is started over on the next write, which forgets every
  answer rather than failing open. Fine.
- **env.source in `run`:** the question is asked from `env.Stack.Prepare`,
  before the first shell starts, whatever starts it: a run, a typed
  command, the History prompt (`Session.AskSized`). `Stop` starts no
  shell and `ErrSourcesNotApproved` stops the run; `ApproveSources ==
  nil` is `Stop`. The TUI pre-answers before anything can start a
  shell and returns `Stop` for a list it hasn't answered
  (`tui/sources.go`). `--yes` approves, as documented; `mdsh --yes -w`
  in CI runs the repository's sourced files, which is the repository's
  own code. An approved file still has to be a regular file of at most
  16 MB. v1.4.0 finding 1 is fixed.
- **The share banner** (`doc/frontmatter.go` `ShareBanner`): names
  outside `env.IsBase` are listed; `-NAME` and base names aren't. The
  CLI's confirm prompt shows `share=` on the block but not the front
  matter's `env.share`; the banner is the TUI's and the GUI's. Fine.
- **Reports and secrets** (`render/render.go` `MaskSecrets`,
  `report.Options.ShowSecrets`): a block marked `secret` prints as
  `(secret)`, code and output, unless `--show-secrets`. Not masked in
  reports: the output of an unmarked block that echoes a variable set
  with `mdsh ctl set --secret`, which mdsh-gui and `mdsh -i` do mask on
  screen (`run.NamesAny`); and `mdsh doc.md` on the terminal, which is
  the person's own screen. A `--pdf` of a run whose unmarked block
  printed `$TOKEN` ships it. Worth one line in the `secret` docs, or
  the same `NamesAny` rule in reports.
- **The shell rc wrapper** (`cmd/mdsh-gui/shellrc`): the block in
  `.zshrc` and `.bashrc` defines `mdsh` as `command mdsh --source <(…)`
  and loads completion with `source <(command mdsh completion …)`, so
  every interactive shell runs whatever `mdsh` is first on `PATH`.
  That's the person's own `PATH`; it is also what makes finding 1 land
  in every terminal. `ZshWrapperState` rewrites an older block in
  place when Settings opens, without a click; `Set` writes the rc file
  in place rather than by rename, so a crash mid-write truncates it.
  Both small; the second is one `os.CreateTemp` away.
- **The Events tab** (`notebook/events.go`): shows the audit events as
  `audit.Log` writes them, so a `var` event for a plain `mdsh ctl set`
  carries the value and a `--secret` one its HMAC, as the log does; the
  new `args` event carries the run's arguments. Copy gives the JSON.
  Nothing new leaks; the tab is the log.
- **Front matter that doesn't parse** (`doc/fixfrontmatter.go`,
  `run/session.go` `checkFrontMatter`): with `FrontMatterErr` set,
  `Options` are the defaults (base share set, `/bin/sh`), every run
  path refuses with `FrontMatterError`, `AskSized` too, so the History
  pane can't start a shell; `mdsh FILE` exits with the error and
  `--no-run` prints with a warning; includes still read, inside the
  root. "Add quotes" only quotes plain values and offers itself only if
  the result parses; it's an undoable edit, and the shells start again
  with the new settings through `ErrFrontMatterFixed`, which asks the
  env.source question again. Fine.
- **Links** (`links.go`): `file:` and bare paths resolve from the
  document's folder; `.md` opens in a tab (which is opening a document,
  with its own questions), images go through `underDoc` and the
  `/doc/` route, and everything else is revealed, or opened only when
  its extension is in Settings › Files and `openable` says regular file
  without the exec bit. `OpenTypes` is empty by default and
  `CleanTypes` lower-cases and trims it. On macOS, `.terminal`,
  `.inetloc`/`.webloc` and `.workflow` files do things when opened
  with `open`, so a person who adds those types has opened that door
  themselves; a note in the setting's text would help. See finding 2
  for Linux.
- **`/doc/` route** (`docfiles.go`): serves only `docTypes` by the
  *resolved* path's extension, regular files, under an open document's
  folder, with `nosniff` and the sandboxing CSP. v1.4.0 finding 12 is
  fixed. `.svg` is served as an image; with `default-src 'none';
  sandbox` a navigated-to SVG can't script. Fine.
- **Settings file** (`settings/settings.go` `write`): 0600 by temp
  file and rename in a 0700 folder, through a symlink if the file is
  one. Fixed. New in it: `fileViews` (per-file view and History state,
  which decides whether a file opens with the History pane, and so
  whether its shell starts on open, now behind the env.source
  question), `openTypes`, `cliPaths` (finding 1).
- **`RememberView`, `SetSettings`, `AnswerOutside`, `ReplaceCast`**: all
  reachable from the page, as every exported `App` method is.
  `RememberView` takes any absolute path and `AnswerOutside` any of
  "allow", "deny", ""; both act only on the stored answer for a file
  the page has. `ReplaceCast` reads and writes through `docroot`.
  Fine.
- **The vendored copy** (`cmd/mdsh-gui/vendor/github.com/gdey/markdownshell`):
  identical to the root packages at the tag for every package the GUI
  uses (`diff -r`, tests excluded), so the GUI has every fix the CLI
  has. PR #208's note that CI doesn't check this still stands; a `go
  mod vendor && git diff --exit-code` step in `go.yml` would.
- **Shell keeping** (`env/shell.go` `interrupt`, `KillAfter`): Stop now
  sends SIGINT to the process group and keeps the shell; `mdsh` kills
  after 5 s, mdsh-gui asks. A block that traps INT keeps running until
  then, which was true of ctrl+c before. The `_mdsh_in` trap and
  `return 130` are inside the shell the block already owns. Nothing
  new for the model.
- **Control socket** (`ctl/`, `run/ctl.go`): unchanged in what it

## Heads-up: what the v1.4.0 review deferred

- **`mdsh --serve` (PR #208)** is still open and still not in a
  release. The six points in the v1.4.0 heads-up stand. Finding 3 and
  4 here add one: under `--serve`, the `/doc/` route and the outside
  question are reachable from a browser, and the root for a document
  in `~` is `~`.
- **Running a document from a URL** (`docs/install/design.md`, "nothing
  here is built") is the next place the root matters: a remote
  document has no folder, so its root should be empty (no includes, no
  `out=` to disk except its own assets folder), and `run.Options.Remote`
  (`Strict` share) should imply that. The design says "reads no local
  file"; `docroot.Root("")` today is the working directory, which for
  `mdsh https://…` would be wherever the shell is. Decide this before
  the first URL fetch lands.
- **The control socket's ask/confirm** is in flight elsewhere; when it
  lands, the question should show what finding 10's fix shows on the
  CLI: the block's `env=`, `share=` and `out=`.
