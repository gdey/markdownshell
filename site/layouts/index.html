Markdown that runs

Your runbook, as an app.

mdsh turns the markdown you already have into something that runs, and turns each run into a record you can send. Open a file in the desktop app, press play on a block, and the output lands under it, in the file, where git and your team can see it.

What it feels like

A notebook, but the kernel is the shell you already use, and every cell is a step someone can read before they run it.

01

Edit on the left. Run on the right.

The source and the rendered notebook side by side, kept in step as you scroll. Press play on a block, a heading, or Run all, and the output streams in under it.

Drag blocks to reorder them, fold sections, undo anything. Close the window and the run is in the file.

02

Guard rails you can see.

confirm asks before the risky step. depends= runs what a block needs first, and the app draws it as lines in the margin. timeout= kills a hang, run=once skips a slow fetch, and on_error: stop ends a bad deploy.

Blocks a printout would hide are drawn anyway, badged, so a file can't run code you never saw.

{{ partial "shot.html" (dict "name" "depends" "title" "guardrails.md" "alt" "A deploy block selected, with colored lines in the margin running up to the login and fetch blocks it depends on") }}
03

Your terminal session becomes a document.

Open the History pane and work as you would in a terminal, with your shell's own prompt and completion. Every command lands in the file as a block, with its output. A line that starts with # becomes a note.

New Session opens a file for the day. When you're done, delete what didn't matter, write a sentence above what did, and the investigation is a runbook.

{{ partial "shot.html" (dict "name" "history" "title" "2026-11-02.md · History" "alt" "The History pane at the bottom of the window, with the commands typed into it appearing above as blocks with their output") }}
04

A form, written in markdown.

textbox and choice blocks become a text field, radio buttons and checkboxes. Pick the environment, type the host, press Run section. What you picked is saved in the file and reaches the blocks as $MDSH_VAR_env.

The author controls the choices; the person running it never edits code.

05

Diagrams, tables and pictures, inline.

A d2 fence draws a diagram, an svg fence a picture. out=markdown turns a block's output into a table, out=image keeps the chart it printed, and tty blocks run on a real terminal and keep a recording.

Nothing is fetched from the network to draw them.

06

One click to the report.

Create Report makes a PDF, a standalone HTML page or a markdown copy of the run, with or without the code, and shows the mdsh command that makes the same one, so CI can make it next week.

The change ticket asked what you ran and what happened. This is that, with exit codes.

Who it's for

  • The runbook is the record.

    Platform and SRE teams. The runbook lives in the repo, runs one confirmed step at a time, and the last run is in git. --pdf makes the evidence for the change ticket, --audit a JSON log for the SIEM.

  • A notebook whose kernel is your shell.

    Analysts whose tools are psql, duckdb, jq and curl. Type in History, keep what mattered, quote a number in the prose, refresh the whole report with one click.

  • Your notes, but they run.

    Solo developers and consultants. Add a shebang to notes.md and ./notes.md runs it. Keep a README's sample output true. Hand a client a setup checklist that checks itself.

Start with the examples.

The repo's examples/ folder is a guided tour in nine parts, from a two-block hello to whole runbooks. The app shows it as collections on its start screen, and every part has a Try it block that runs the example it describes.

  1. Get the code and the tour. {{ highlight `git clone https://github.com/gdey/markdownshell cd markdownshell/examples` "sh" "" }}
  2. Open the folder in the app, or in the terminal UI. {{ highlight `mdsh-gui . # or: mdsh -i` "sh" "" }}
  3. Start with README.md, then hello.md. Pin the runbooks you come back to.

One file, three ways to run it.

The desktop app, the terminal UI and the command line share one engine, so a document runs the same in all three and saves the same bytes.

  • Shipping

    Desktop app

    Tabs, the start screen with collections and pins, source beside rendered, History, Console, outline, diagrams. macOS and Linux.

    {{ highlight `mdsh-gui runbooks/` "sh" "" }}
  • Shipping

    Terminal UI

    The same notebook over SSH: outline, block moves with undo, reports, tabs, and a History pane with your shell's prompt.

    {{ highlight `mdsh -i deploy.md` "sh" "" }}
  • Shipping

    Command line

    Run in CI, write output back, make PDF and HTML reports, keep an audit log. One static binary.

    {{ highlight `mdsh --yes -w deploy.md` "sh" "" }}

Coming: blocks that run over SSH on the machine they belong to, and a notebook served to a browser. See the roadmap.

All the ways to install

Safe to open

Opening a file runs nothing. A document reads only the environment variables you expose, never loads images from the network, and can't hide code from the question that asks to run it. The security reviews are public, and every High finding in them is fixed.
