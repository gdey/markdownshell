Markdown that runs

Your runbook, as an app.

mdsh turns the markdown you already have into something that runs, and turns each run into a record you can send. Open a file in the desktop app, press play on a block, and the output lands under it, in the file, where git and your team can see it.

Get the desktop app Take the tour

Also a CLI and a terminal UI: brew install gdey/tap/mdsh. Free and open source, MIT.

New in 1.7

  • Earlier runs. Mark a block history=N and the file keeps the runs before the last one under it, each with its time and exit status. The app and mdsh -i show them, and --history puts them in a report.
  • When it ran. Every output says how long ago its run started, "6 mins ago", kept current, with the exact time a hover away.
  • A History pane that keeps up. It shows the shell's working directory, fills the tab at a click (or Z), and takes a whole block typed into it, from # ```sh to ```, added to the file without running. Its record button turns recording off, so commands run without landing in the file.
  • What's still running. The Console's Processes tab, and P in mdsh -i, show every process under the file's shells, with how long it has run and a Kill. A background block that outlives its run can be stopped from its card.
  • Load image. An image from another site, or outside the document's folder, waits behind a button; one click loads it, and the document remembers.
  • Green Tea. A sheet of washi on a tatami mat beside a bowl of matcha, in light and at evening.
  • HTTP docs and a body fold. A docs page and a seventh part of the tour for http blocks, and a response body that folds on its own.

Plus fixes from the 1.7 security review, a <details> that folds the markdown inside it, and mdsh --serve in an mdsh built with -tags serve. 1.6 brought http blocks, mdsh ctl ask and confirm, HTML drawn from your markdown, and the Coffee look; 1.5 settings and the cheat sheet in tabs, front matter that opens even when it doesn't parse, and Witchcraft. Every change is in the changelog.

What it feels like

A notebook, but the kernel is the shell you already use, and every cell is a step someone can read before they run it.

01

Edit on the left. Run on the right.

The source and the rendered notebook side by side, kept in step as you scroll. Press play on a block, a heading, or Run all, and the output streams in under it.

Drag blocks to reorder them, fold sections, undo anything. Close the window and the run is in the file.

{{ partial "shot.html" (dict "name" "split" "title" "deploy.md · source and rendered" "alt" "The deploy runbook with its markdown source on the left and the rendered notebook on the right") }}
02

Guard rails you can see.

confirm asks before the risky step. depends= runs what a block needs first, and the app draws it as lines in the margin. timeout= kills a hang, run=once skips a slow fetch, and on_error: stop ends a bad deploy.

Blocks a printout would hide are drawn anyway, badged, so a file can't run code you never saw.

{{ partial "shot.html" (dict "name" "depends" "title" "guardrails.md" "alt" "A deploy block selected, with colored lines in the margin running up to the login and fetch blocks it depends on") }}
03

Secrets stay out of the file.

Mark a block secret and the app blurs its code and output until you press the eye, then masks them again after a minute. Mark it nosave and it runs as usual, but its output is never written to the file, so it never reaches git.

A running block counts up against its timeout=, and every block keeps how long it took.

04

Your terminal session becomes a document.

Open the History pane and work as you would in a terminal, with your shell's own prompt and completion. Every command lands in the file as a block, with its output. A line that starts with # becomes a note.

New Session opens a file for the day. When you're done, delete what didn't matter, write a sentence above what did, and the investigation is a runbook.

05

A form, written in markdown.

textbox and choice blocks become a text field, radio buttons and checkboxes. Pick the environment, type the host, press Run section. What you picked is saved in the file and reaches the blocks as $MDSH_VAR_env.

The author controls the choices; the person running it never edits code.

06

Diagrams, tables and pictures, inline.

A d2 fence draws a diagram, an svg fence a picture. out=markdown turns a block's output into a table, out=image keeps the chart it printed, and tty blocks run on a real terminal and keep a recording.

Nothing is fetched from the network to draw them.

07

One click to the report.

Create Report makes a PDF, a standalone HTML page or a markdown copy of the run, with or without the code, and shows the mdsh command that makes the same one, so CI can make it next week.

The change ticket asked what you ran and what happened. This is that, with exit codes.

08

Call the API. Check what it said.

An http block is a request written the way it goes over the wire. Under it, checks in Hurl's words say what the response must hold, and captures pull out a token or an id for the prose and the next request. The app shows the body and headers in tabs beside the checks.

Credential headers and secret captures are saved masked, so the file can go in git.

What did it say last week?

Mark a block history=N and each run moves the one before it down, so the file keeps the last N runs under the current output, each with when it ran and how it exited. Every output says how long ago it ran.

A failure from Friday stays in the file, next to today's success, and in git.

Who it's for

  • The runbook is the record.

    Platform and SRE teams. The runbook lives in the repo, runs one confirmed step at a time, and the last run is in git. --pdf makes the evidence for the change ticket, --audit a JSON log for the SIEM.

  • A notebook whose kernel is your shell.

    Analysts whose tools are psql, duckdb, jq and curl. Type in History, keep what mattered, quote a number in the prose, refresh the whole report with one click.

  • Your notes, but they run.

    Solo developers and consultants. Add a shebang to notes.md and ./notes.md runs it. Keep a README's sample output true. Hand a client a setup checklist that checks itself.

One file, four ways to run it.

The desktop app, the terminal UI, the command line and the browser share one engine, so a document runs the same in all four and saves the same bytes.

  • Shipping

    Desktop app

    Tabs, the start screen with collections and pins, source beside rendered, History, Console, outline, diagrams. macOS and Linux.

    {{ highlight `mdsh-gui runbooks/` "sh" "" }}
  • Experimental

    Browser

    The desktop app's notebook in a web browser, on this machine by default and behind a token. Only in an mdsh built with -tags serve; release builds leave it out. See Browser.

    {{ highlight `mdsh --serve deploy.md` "sh" "" }}
  • Shipping

    Terminal UI

    The same notebook over SSH: outline, block moves with undo, reports, tabs, and a History pane with your shell's prompt.

    {{ highlight `mdsh -i deploy.md` "sh" "" }}
  • Shipping

    Command line

    Run in CI, write output back, make PDF and HTML reports, keep an audit log. One static binary.

    {{ highlight `mdsh --yes -w deploy.md` "sh" "" }}

Coming: blocks that run over SSH on the machine they belong to. See the roadmap.

Safe to open

Opening a file runs nothing. A document reads only the environment variables you expose, never reaches the network for an image you didn't click to load, and can't hide code from the question that asks to run it. The security reviews are public, and every High finding in them is fixed.
